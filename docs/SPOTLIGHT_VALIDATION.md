### 文件与文件夹剪贴板扩展

用户随后要求在剪贴板显示 Finder 复制的文件。记录现在区分文本与文件路径组；单文件、文件夹和多个项目都可记录，多选复制保存为一条历史。文件名、路径、来源可搜索，列表显示名称、数量、位置和可见行图标；支持恢复整组文件 URL、在 Finder 显示、复制路径与删除历史。删除历史不删除实际文件，恢复前任一路径失效都保留当前剪贴板并显示错误。只保存路径引用，不读取或备份文件正文。旧文本加密归档可直接读取，AES-GCM v1 格式保持兼容。图片正文、未生成的 file promise 和混合无效项目仍不采集。

首个文件扩展 Release 构建在当前系统实测：在 Finder 选中合成文本文件和含嵌套文件的文件夹，按 ⌘C 后出现一条「2 个文件」记录；在历史中按 ⌘C，再到空目标目录按 ⌘V，两个项目均复制成功。文本文件及文件夹内文件的 SHA-256 与源文件逐项一致，忽略 Finder 自行生成的 `.DS_Store`；证据为 `build/validation/file-clipboard-finder-check.json`。自身恢复复制没有增加重复记录。测试条目通过其专用名称筛选并删除，未清空其他历史。

进一步检查发现，临时签名构建读取旧钥匙串项目时，后台 `SecItemCopyMatching` 可等待系统安全对话框。进程采样见 `build/validation/file-clipboard-process-sample.txt`。后台请求现同时抑制 LAContext 和传统 Keychain 的交互，恢复调用前的进程内状态；失败立即显示内存暂存提示，保留原密文。设置提供「授权保存历史」，只在用户点击后请求交互授权；成功读回原归档才合并当前记录并保存。自动化覆盖拒绝后重试、旧文件历史与内存记录合并、失败存储不被覆盖，以及交互状态恢复。传统 SecKeychain 接口在当前 SDK 中已弃用，此处用于兼容既有传统钥匙串项目。

最终 Release 安装到 `/Applications/Oil Find.app`，可执行文件、Info.plist、图标与构建包逐项一致，签名完整性验证通过。可执行文件 SHA-256：`baad1bccaa9aebc96ad126d85f04384ef98a5d83a85fd9bdfce2390921291bed`；安装证据为 `build/validation/file-clipboard-installed.json`。最终版实际按 ⌘Space 唤起并按 ⌘4 切换成功；用户的开启状态、30 天、1,000 条及排除名单保留。当前系统拒绝最终版对旧密钥的后台访问，设置显示「无法访问钥匙串；新内容暂存内存」和授权按钮；等待用户手动授权，尚不能宣称最终版重启恢复已在实机通过。原密文保留，没有更改钥匙串 ACL 或辅助功能权限。自动化粘贴安全分支通过；本次 Finder 实测采用历史 ⌘C 后手动 ⌘V。

### 文件引擎对照

机器为 Apple M1 Pro、16 GiB、macOS 26.3.1(a)，两种 CLI 用同一个 Swift 6.3.3 工具链以 Release 构建，独立 scratch 目录。基准对应原作者上述提交；C、CLI 和搜索/索引核心源码均相同，Core 只有快捷键和新增设置默认值变化。

使用同一只读索引副本，446,042 条，15,566,065 字节，SHA-256 `52bb6010e8a2e34e9699e04f18717ce5b8aaa70cde66fccb77f42818052d70d4`。25 个查询及 `typing readme`，每版本 12 轮，每轮每项 20 次，交替 AB、BA，共每项每版本 240 次。CLI 不暴露单次原始延迟，表格指标是 **12 轮各自 p95 的中位数**，不是合并 240 次的 p95。所有轮次报告的结果数量相同。原始表和范围见 `build/validation/benchmark-engine-abba-12/summary.tsv` 与 `comparison.json`。

| 查询 | 原作者每轮 p95 的中位数 | 新版每轮 p95 的中位数 | 差异 |
| --- | ---: | ---: | ---: |
| a | 9.425 ms | 9.575 ms | +1.6% |
| e | 10.637 ms | 11.141 ms | +4.7% |
| readme | 1.106 ms | 1.127 ms | +1.9% |
| file:readme | 1.307 ms | 1.319 ms | +1.0% |
| package.json | 0.432 ms | 0.415 ms | -4.1% |
| 文档 | 0.278 ms | 0.276 ms | -0.7% |

`typing readme` 每次取正向输入与退格各步的最大耗时，再对 20 次最大值取 p95；不是所有按键的 p95。最初 4 轮曾测得 a +28.6%，范围波动较大，因此扩大到 12 轮而非只选取有利数据。26 项跨轮指标的相对差异中位数约 +1.4%，不能当作总体 p95，也不是统计显著性结论。另用完全相同的原作者二进制做 4 轮同样对照：a +9.0%、readme -2.7%、file:readme -6.7%、typing -17.0%，见 `benchmark-engine-control/`；说明进程调度和缓存会造成可见波动。e 的同二进制对照较稳定，仍不能抹去新版这一轮测得的 +4.7%。结论是未见大的稳定引擎退化，存在小幅差异，不能宣称零损失。

整 CLI 的峰值 RSS 跨轮中位数为原版约 59.0 MiB、新版约 60.5 MiB，范围重叠；这个进程不运行剪贴板或应用目录，不能拿它估计完整 App 的新增内存。测量结束后全部临时索引副本已删除；对照脚本现在在成功和失败路径都清理副本，保留 checksum 和结果。
